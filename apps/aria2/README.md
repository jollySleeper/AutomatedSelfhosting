# aria2 + AriaNg - Lightweight Download Manager

aria2 is an ultra-fast, multi-protocol download utility supporting HTTP/HTTPS, FTP, SFTP, and BitTorrent. AriaNg provides a modern web UI for managing downloads.

## Quick Reference

| Property | Value |
|----------|-------|
| **aria2 Image** | `docker.io/p3terx/aria2-pro:latest` |
| **AriaNg Image** | `docker.io/p3terx/ariang:latest` |
| **RPC Port** | 8062 (host) → 6800 (container) |
| **Web UI Port** | 8063 (host) → 6880 (container) |
| **BT Port** | 6888 (TCP/UDP) |
| **Subdomain** | `ariang.aevion.lan` |

## RPC Endpoints (IMPORTANT)

aria2 1.36 exposes its RPC over HTTP at **two distinct paths** — they are NOT interchangeable:

| Path | Protocol | Used by |
|------|----------|---------|
| `/jsonrpc` | JSON-RPC over HTTP POST (`Content-Type: application/json`) | AriaNg (browser), most modern clients, JS/Python SDKs |
| `/rpc` | XML-RPC over HTTP POST (`Content-Type: text/xml`) | Prowlarr, Sonarr, Radarr, Lidarr, Readarr (Servarr stack uses `CookComputing.XmlRpc`) |

> Sending an XML-RPC body to `/jsonrpc` (or vice versa) results in `{"error":{"code":-32700,"message":"Parse error."}}` — that error is the canonical sign you've used the wrong endpoint.

## Access

- AriaNg Web UI: `http://ariang.aevion.lan` (HTTP) or `https://ariang.aevion.lan` (HTTPS)
- aria2 JSON-RPC (browser, via nginx): `http://ariang.aevion.lan/jsonrpc` — same origin as AriaNg, proxied by `apps/nginx/configs/sites/ariang.conf`
- aria2 RPC (host loopback, for *arr containers): `http://10.0.2.2:8062/{jsonrpc,rpc}`

## AriaNg Initial Setup (browser)

AriaNg is a 100% static web app — the RPC connection is made **from your browser**, not from the AriaNg container. The nginx site `ariang.aevion.lan` proxies `/jsonrpc` to aria2 so the browser can use the same origin (no CORS, no port issues).

1. Open `http://ariang.aevion.lan`
2. Go to **AriaNg Settings → RPC**
3. Set:
   - Aria2 RPC Address: `ariang.aevion.lan` (no port — uses default 80/443)
   - Aria2 RPC Protocol: `http` (or `https`)
   - Aria2 RPC HTTP Request Method: `POST`
   - Aria2 RPC Path: `/jsonrpc`
   - Aria2 RPC Secret Token: value of `RPC_SECRET` from `environments/local.env`
4. Click **Activate** at the top
5. The "Aria2 Status" badge in the sidebar should turn green
6. **Important**: Change `RPC_SECRET` in `environments/local.env` before deploying to production

## Prowlarr / Sonarr / Radarr / Lidarr / Readarr Setup

These apps use **XML-RPC**, so they need path `/rpc`, not `/jsonrpc`.

1. In the *arr app: Settings → Download Clients → Add → **Aria2**
2. Configure:
   - Host: `10.0.2.2` (host loopback via pasta network)
   - Port: `8062`
   - **XML RPC Path: `/rpc`** ← critical
   - Secret Token: value of `RPC_SECRET` from `environments/local.env`
3. Click **Test** — should succeed

## Volumes & bind-mounts

| Container path | Host path | Mode | Purpose |
|----------------|-----------|------|---------|
| `/config` | `apps/aria2/volumes/config` | rw | Runtime config volume — `aria2.conf` (generated by image, then layered with our overrides at every boot), `aria2.session`, hook scripts, DHT state |
| `/downloads` | `~/media/Downloads/aria2` | rw | Downloaded files (shared with the *arr stack via `~/media`) |
| `/etc/cont-init.d/48-apply-overrides` | `apps/aria2/scripts/apply-overrides.sh` | ro | s6-overlay drop-in that applies our overrides at boot — see [Aria2 conf overrides](#aria2-conf-overrides-source-of-truth-in-this-repo) |
| `/etc/aria2-overrides.conf` | `apps/aria2/configs/local.aria2.conf.overrides` | ro | The list of overrides the script reads. Live bind-mount — edits take effect on the next `systemctl --user restart aria2` |

## Comparison with qBittorrent

See `apps/qbittorrent/README.md` for a feature comparison table.

**TL;DR**: qBittorrent is the primary download client for the *arr stack (richer category/queue management). aria2 is great as a secondary client for direct HTTP/FTP downloads, magnet links, and lightweight torrenting. Both can coexist in Prowlarr/Sonarr as parallel download clients with different priorities.

## Aria2 conf overrides (source of truth in this repo)

The p3terx image generates `/config/aria2.conf` on first start with sensible defaults — but a few don't suit our setup (most importantly `force-save=false`, which silently drops AriaNg's stopped queue on every restart). Rather than fork the whole conf, we keep a small repo-tracked list of overrides and apply them **inside the container at every boot** via the image's own s6-overlay init system.

### Files in the repo

```
apps/aria2/
├── configs/
│   ├── sample.aria2.conf.overrides   # full reference, all common tunables documented
│   └── local.aria2.conf.overrides    # ACTIVE overrides — read at every container boot
└── scripts/
    └── apply-overrides.sh            # s6 cont-init.d drop-in that does the patching
```

### How it works (s6-overlay cont-init.d extension)

The p3terx image runs **s6-overlay** as PID 1 (`/init`). At boot, s6 runs every executable in `/etc/cont-init.d/` **in alphabetical order** before any service starts. The image already ships:

```
/etc/cont-init.d/
├── 00-copyright       # banner
├── 01-set-id          # set container UID/GID
├── 02-set-timezone    # apply $TZ
├── 08-config          # download aria2.conf if missing, install hook scripts
├── 18-mode            # configure SPECIAL_MODE (rclone/move)
├── 28-fix             # apply env-driven sed: RPC_PORT, RPC_SECRET, DISK_CACHE, …
├── 58-permissions     # chown /config and /downloads
└── 88-done            # final banner
```

`podman-setup.sh` bind-mounts our `apply-overrides.sh` into that directory as **`48-apply-overrides`** (and our `local.aria2.conf.overrides` to `/etc/aria2-overrides.conf`). Number `48` is deliberate:

- **After `28-fix`** — so our overrides win against the image's env-driven substitutions (e.g., `disk-cache=` from `DISK_CACHE` env)
- **Before `58-permissions`** — so our edits to `/config/aria2.conf` get the right ownership applied
- **Before any service starts** — so aria2c reads the final, patched conf at startup. No restart loop, no `podman exec`-from-outside, no race conditions.

### What the script does

For each `key=value` line in `/etc/aria2-overrides.conf`:

1. If `^key=` exists in `/config/aria2.conf` → `sed`-replace it
2. Otherwise → append the line

Comments (`#…`) and blank lines are skipped. Output is logged with the same `[INFO]`/`[WARN]` colour helpers the image's own cont-init scripts use (`/etc/init-base`), so the boot log is consistent. The script is fully idempotent — re-running it converges on the same state.

### Adding a new override

```bash
# 1. Pick a key from the reference (or any option in the aria2 manual)
$EDITOR apps/aria2/configs/local.aria2.conf.overrides

# 2. Roll it out — no podman-setup.sh re-run needed because the override file
#    is bind-mounted live into the container
ssh legion@aevion 'systemctl --user restart aria2'

# 3. Verify
ssh legion@aevion 'podman logs aria2 2>&1 | grep apply-overrides'
```

The `sample.aria2.conf.overrides` lists the tunables we've found most useful (concurrent downloads, connection caps, BT seed time/ratio, disk cache, etc.) with comments explaining defaults — start there before consulting the [full aria2 manual](https://aria2.github.io/manual/en/html/aria2c.html#options).

### Harmless boot-log warning

Because the script is bind-mounted read-only, you'll see this in the container log every boot:

```
s6-chown: fatal: unable to chown /var/run/s6/etc/cont-init.d/48-apply-overrides: Read-only file system
s6-chmod: fatal: unable to change mode of /var/run/s6/etc/cont-init.d/48-apply-overrides: Read-only file system
```

s6-overlay tries to normalise ownership/permissions on every cont-init script and fails on the read-only bind mount — but it then proceeds and runs the script anyway (you'll see `48-apply-overrides: executing… applied 2 override(s)` immediately below). The mount stays read-only deliberately: in our rootless setup, the container's "root" maps to the host user, so a writable mount would let s6 actually chown the host file.

### Why a cont-init drop-in instead of an entrypoint hack

`apps/jellyfin/podman-setup.sh` uses `--entrypoint /entrypoint.sh` to fully replace the image's entrypoint, because the official jellyfin image runs the binary directly (no init system). That pattern would be wrong here: replacing `/init` would force us to re-implement (or invoke) the entire s6 boot chain ourselves. Dropping a script into `cont-init.d` is the image's own intended extension point — fewer moving parts, no fight with future image updates.

### History persistence (`force-save`)

AriaNg has no history of its own — it just calls `aria2.tellStopped` over RPC. The stopped/completed/error queue lives in aria2's RAM, capped by `max-download-result`. With the image's default `force-save=false`, the on-disk session file (`/config/aria2.session`, written every second) only contains active and waiting downloads, so any aria2 restart wipes the entire stopped queue and AriaNg shows an empty history.

The active overrides fix this:

```ini
force-save=true               # session also persists completed/error/removed
max-download-result=10000     # in-memory ring buffer (default 1000)
```

Verify the live values:

```bash
curl -s -d '{"jsonrpc":"2.0","id":"q","method":"aria2.getGlobalOption","params":["token:<RPC_SECRET>"]}' \
  http://127.0.0.1:8062/jsonrpc | jq '.result | {force-save, "max-download-result"}'
```

## Identifying partial vs complete files on disk

Because `aria2.conf` uses `file-allocation=falloc`, every download — even a 5%-complete one — pre-reserves the **full** target size on disk, so `ls -l`, `stat -c %s`, and `du` all report 100%. The only reliable on-disk signal is the `.aria2` control file:

| State on disk | Meaning |
|---|---|
| `foo.mkv` and `foo.mkv.aria2` both present | **Incomplete** — control file holds the piece bitfield |
| `foo.mkv` alone | Complete (the p3terx `clean.sh` hook removes `.aria2` on success) |

Find every partial file under the downloads directory:

```bash
find ~/media/Downloads/aria2 -name '*.aria2' -printf '%p\n' | sed 's/\.aria2$//'
```

To safely delete a partial download (data + control file):

```bash
rm -v "/path/to/file.ext" "/path/to/file.ext.aria2"
```

For exact completion percentages on tasks aria2 still remembers, query the RPC directly:

```bash
curl -s -d '{"jsonrpc":"2.0","id":"q","method":"aria2.tellStopped","params":["token:<RPC_SECRET>",0,1000,["status","completedLength","totalLength","errorCode","files"]]}' \
  http://127.0.0.1:8062/jsonrpc | jq
```

## Troubleshooting

| Symptom | Cause | Fix |
|---------|-------|-----|
| Prowlarr "Unable to connect to Aria2", aria2 logs `Failed to parse JSON-RPC request` | Path is `/jsonrpc` (Prowlarr sends XML-RPC) | Change path to `/rpc` |
| AriaNg "Disconnected" with port `:8063` in RPC address | Port 8063 is the static UI, not the RPC | Use `ariang.aevion.lan` (no port) with path `/jsonrpc` |
| AriaNg "Disconnected" with port `:8062` in RPC address | Port 8062 is bound to `127.0.0.1` on the host, browsers can't reach it | Use `ariang.aevion.lan` (no port) — it's proxied through nginx |
| `Unauthorized` from aria2 | Wrong/missing secret token | Token is `token:<value>` in JSON-RPC params; in Prowlarr/AriaNg just enter the value (no `token:` prefix) |
| AriaNg's "Stopped" tab is empty after a refresh / container restart | aria2 ships with `force-save=false`, so the stopped queue is RAM-only | See [History persistence](#history-persistence-force-save) above — `local.aria2.conf.overrides` already enforces `force-save=true` and is re-applied at every container boot by `48-apply-overrides` |
| File on disk shows full size but is actually partial | `file-allocation=falloc` pre-reserves all blocks | Look for a sibling `.aria2` control file — see [Identifying partial vs complete files](#identifying-partial-vs-complete-files-on-disk) |
