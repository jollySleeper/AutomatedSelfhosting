# Vaultwarden - Bitwarden-compatible Password Manager

Vaultwarden is a lightweight, unofficial implementation of the Bitwarden server
API. It works with the official Bitwarden web vault (bundled in the image),
browser extensions, desktop, mobile and CLI clients.

## Quick Reference

| Property | Value |
|---|---|
| **Image** | `docker.io/vaultwarden/server:1.37.3` (bundled web vault 2026.7.0) |
| **Container** | `vaultwarden` |
| **Internal port** | `8080` (`ROCKET_PORT`) |
| **Host port** | `127.0.0.1:8035` |
| **URL** | `https://vault.aevion.lan` |
| **Aliases** | `vw.aevion.lan`, `vaultwarden.aevion.lan` (redirect to the URL above) |
| **Admin panel** | `https://vault.aevion.lan/admin` |
| **Database** | SQLite at `volumes/data/db.sqlite3` |
| **Systemd service** | `vaultwarden.service` (user) |

## Access

The vault is HTTPS-only. The web vault needs a secure context for the Web
Crypto API, so NGINX redirects every HTTP request, and both aliases, to
`https://vault.aevion.lan`. That hostname must match `DOMAIN` in `local.env`
because passkeys and WebAuthn are bound to it.

LAN and Tailscale clients resolve the name through AdGuard Home's
`*.aevion.lan` rewrite. A Mac whose VPN replaces the resolver needs an
`/etc/hosts` entry:

```text
192.168.1.105 vault.aevion.lan vw.aevion.lan vaultwarden.aevion.lan
```

### Trusting the certificate

NGINX serves the `*.aevion.lan` certificate signed by the private CA at
`~/certs/ca.pem` on aevion. Bitwarden apps refuse untrusted certificates, so
install and trust that CA on every device that uses the vault (see
[`docs/SSL_SETUP_SUMMARY.md`](../../docs/SSL_SETUP_SUMMARY.md) for macOS).
Browsers and extensions use the operating system's trust store; Firefox keeps
its own store.

### Client configuration

In each Bitwarden client, choose **Self-hosted** on the login screen and set
the server URL to `https://vault.aevion.lan`.

## Initial Setup

Registration is closed (`SIGNUPS_ALLOWED=false`) and SMTP is not configured,
so accounts are created through admin invitations:

1. Read the generated admin password on aevion, store it in your password
   manager, then delete the file:
   ```bash
   cat ~/selfhost/apps/vaultwarden/volumes/admin-password.txt
   rm ~/selfhost/apps/vaultwarden/volumes/admin-password.txt
   ```
2. Log in at `https://vault.aevion.lan/admin`, open **Users**, and invite your
   email address.
3. Open `https://vault.aevion.lan/#/signup`, enter the invited address, and set
   a strong master password. Without SMTP there is no password recovery, so
   keep an emergency copy of the master password somewhere safe.
4. Enable two-step login in **Settings → Security → Two-step login**
   (authenticator app or a FIDO2 security key).

To rotate the admin password, run `./scripts/set-admin-token.sh` and restart
the service. If you ever save settings in the admin panel, they are written to
`volumes/data/config.json` and override `local.env`.

## Configuration

`environments/local.env` (not committed) contains:

| Variable | Value | Purpose |
|---|---|---|
| `DOMAIN` | `https://vault.aevion.lan` | Canonical URL for clients, attachments and WebAuthn |
| `ROCKET_PORT` | `8080` | Unprivileged listen port; must match `CONTAINER_PORT` in `podman-setup.sh` |
| `SIGNUPS_ALLOWED` | `false` | Only admin-invited emails can register |
| `ADMIN_TOKEN` | Argon2id PHC string | Enables `/admin`; written by `scripts/set-admin-token.sh` |

`environments/sample.env` documents every supported variable. Podman reads env
files literally: never quote values or escape `$` (the upstream template's
quoted `ADMIN_TOKEN` example would be read with the quotes and break admin
login).

## Security Controls

- Runs as `legion` via `--userns keep-id`, never as root.
- Read-only root filesystem; all writes go to `/data`.
- All capabilities dropped, `no-new-privileges`, 512 MB memory and 2 CPU limit.
- Plain pasta networking with no host-loopback access; the port is bound to
  `127.0.0.1` and reachable only through NGINX.
- The admin token is stored as an Argon2id hash; the admin login is rate
  limited (3 attempts, then one per 5 minutes).
- NGINX passes Vaultwarden's own CSP and `X-Frame-Options` through unchanged.
  The site config deliberately avoids `ssl-params.conf`'s `X-Frame-Options:
  DENY`, which would break the WebAuthn and Duo 2FA connector iframes.
- Vault item contents are encrypted by the clients before upload; the server
  never sees the master password or decrypted items.

## Directory Structure

```text
apps/vaultwarden/
├── podman-setup.sh
├── vaultwarden.container          # generated by podman-setup.sh
├── environments/
│   ├── sample.env
│   └── local.env                  # secret, ignored
├── scripts/
│   └── set-admin-token.sh
└── volumes/                       # ignored by git and Syncthing
    ├── admin-password.txt         # delete after storing the password
    └── data/
        ├── db.sqlite3             # vault database (backup required)
        ├── attachments/           # file attachments (backup required)
        ├── sends/                 # Send files (backup optional)
        ├── icon_cache/            # website icons (backup optional)
        ├── rsa_key.pem            # session signing key (backup recommended)
        └── config.json            # only if settings were saved in /admin
```

## Backup & Restore

Create a consistent SQLite snapshot while the service is running:

```bash
podman exec vaultwarden /vaultwarden backup
# Backup to 'data/db_YYYYMMDD_HHMMSS.sqlite3' was successful
```

Copy that file together with `attachments/`, `sends/`, `rsa_key.pem` and
`config.json` (if present) off the server, then delete the snapshot from
`volumes/data/` so snapshots do not accumulate next to the live database.

To restore, stop the service, delete `db.sqlite3-wal` and `db.sqlite3-shm`,
replace `db.sqlite3` with the snapshot and the other files with their backed-up
versions, then start the service:

```bash
systemctl --user stop vaultwarden.service
cd ~/selfhost/apps/vaultwarden/volumes/data
rm -f db.sqlite3-wal db.sqlite3-shm
cp /path/to/db_YYYYMMDD_HHMMSS.sqlite3 db.sqlite3
systemctl --user start vaultwarden.service
```

## Deployment

```bash
cd ~/selfhost/apps/vaultwarden
./scripts/set-admin-token.sh   # first deployment only
bash podman-setup.sh
podman exec nginx nginx -t && podman exec nginx nginx -s reload
```

## Verification

```bash
systemctl --user status vaultwarden.service
podman inspect vaultwarden --format '{{.State.Health.Status}}'
podman logs vaultwarden
curl --cacert ~/certs/ca.pem --resolve vault.aevion.lan:443:127.0.0.1 https://vault.aevion.lan/alive
curl --cacert ~/certs/ca.pem --resolve vault.aevion.lan:443:127.0.0.1 https://vault.aevion.lan/api/config
```

`/api/config` must list `https://vault.aevion.lan` URLs. In the web vault's
browser developer tools, `/notifications/hub` must upgrade with status `101`.

## Updates

The image is pinned to `1.37.3`; `AutoUpdate=registry` only picks up rebuilds
of that tag. To upgrade, back up first, change `IMAGE_SOURCE` in
`podman-setup.sh`, and re-run it. Vaultwarden migrates the database on start,
so a downgrade needs the pre-upgrade backup.

## Known Issues

- **Bitwarden clients 2026.9.x**: `bw` CLI 2026.9.0 cannot log in to 1.37.3
  because it calls `POST /api/accounts/key-management/user-key-id`, which
  returns 404
  ([vaultwarden#7750](https://github.com/dani-garcia/vaultwarden/issues/7750)).
  Server support was merged after 1.37.3
  ([vaultwarden#7693](https://github.com/dani-garcia/vaultwarden/pull/7693))
  and ships in the next release. CLI 2026.8.0 works. Other clients from the
  2026.9 release train may be affected the same way.
- **No mobile push**: WebSocket notifications reach web, desktop and browser
  extension clients only. Mobile apps pick up changes when they sync; instant
  push needs `PUSH_ENABLED` with credentials from
  [bitwarden.com/host](https://bitwarden.com/host).
